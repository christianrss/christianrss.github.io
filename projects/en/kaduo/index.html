Real-time media · social commerce

Kaduo — Real-Time Media and Social Commerce

A commerce system whose distinctive engineering work is the browser-based live production studio, authenticated WebRTC ingest, media relay and commerce-aware video composition. This case study records what the code establishes, what it does not, and how to validate it.

System boundary and architecture

The platform comprises a React/Vite client, a NestJS application API, PostgreSQL for transactional data, Redis for supporting services, ClickHouse for analytics, a separate Node media bridge, OvenMediaEngine (OME), and external video services. Docker Compose defines these components but does not itself prove production availability.

  • Live publishing path: device camera/microphone → browser Canvas compositing → canvas.captureStream() with original audio tracks → RTCPeerConnection offer → authenticated WHIP endpoint in the Node bridge → OvenMediaEngine WebRTC ingest → OME RTMP push → Mux ingest → playback.
  • Control plane: NestJS manages live sessions, stream ownership, status transitions, temporary publish tokens and encrypted stream keys. Socket.IO delivers studio status and telemetry events.
  • Recorded media: browser MediaRecorder captures videos; tus uploads use 5 MiB chunks and retries. Bunny integration handles managed video uploads, playback and webhooks.
  • Commerce plane: catalog, stores, carts, coupons, chat, live products, seller analytics and shopping-agent actions remain in application services rather than in the raw video transport.

Live compositor and studio

The device-camera studio renders a source-video frame into a 2D Canvas and applies ordered visual layers: text, images, ambient effects, product/coupon overlays, live chat, view counters and coupon effects. The canvas track and unmodified source audio tracks form the outgoing stream. Canvas composition means the effects are present in the transmitted pixels, not only as browser-side display elements.

The studio code also contains aspect-ratio and quality controls, device switching, scene presets, layout history and drag interactions, network statistics and WebSocket-mediated studio telemetry. The embedded-text feature is controlled by build/runtime flags; the repository documents verification in the device_camera workflow, not external-encoder mode. The large studio component contains roughly 11,000 lines; this creates a concrete maintainability and testability risk.

Engineering decisions visible in source

  • Browser compositing rather than a server-side renderer: avoids a separate real-time graphics renderer for device broadcasts and keeps the editing experience near the capture source; the trade-off is device CPU/GPU and browser compatibility.
  • WHIP/WebRTC ingress with OME-to-Mux push: separates low-latency browser publishing from managed playback and distribution. The bridge holds ephemeral sessions in a process-local map.
  • Short-lived publication credentials: the backend generates a random token, stores its hash and associates it with an expiring studio session; the bridge compares hashes with timing-safe comparison.
  • Decoupled recording/upload path: MediaRecorder and tus address short-form media separately from live ingest.
  • Structured domain/application/infrastructure layers: helps isolate commerce semantics from streaming transport. The separation is visible in module paths; its complete enforcement was not independently audited.

Alternatives and trade-offs

The following are engineering comparisons, not documented historical choices of the author.

  • Server-side FFmpeg/GStreamer mixing could improve rendering consistency and multi-camera control, but requires transcoding infrastructure and more operational work.
  • Direct RTMP via OBS handles external encoders and advanced production; a camera-native web studio reduces friction on phones. The application exposes both transmission modes.
  • Managed ingest end-to-end (without OME) could reduce self-hosted infrastructure, but would change the browser publication path and provider coupling.
  • A dedicated media control database/Redis store could preserve ephemeral sessions across bridge restarts, unlike the present in-memory map.

Evidence of tests and reproducibility

Source-level evidence (tests were inspected, not executed here):

  • backend/test/streaming.controller.spec.ts — forwarding of signed Mux/Bunny webhook raw bodies and rejection when raw bodies are missing.
  • backend/test/manage-live-stream-webhooks.spec.ts — malformed payloads and invalid webhook signatures.
  • backend/test/ads-delivery-event.utils.spec.ts and backend/test/analytics-events.spec.ts — analytics-related unit coverage.
  • docs/live-embedded-text.md — manual smoke-test procedure confirming embedded text in the published stream.
  • docker-compose.yml and media-server/oven/Server.xml — deployment topology and codec/profile configuration (H.264, AAC).

Run backend tests using the repository's test:unit script after provisioning dependencies. For true streaming verification, add a controlled browser/device matrix and an isolated OME + Mux staging environment; record timestamps, jitter, failures, CPU and end-to-end latency.

Limits, risks and next measurements

Not yet established by the inspected evidence: actual audience concurrency, p95 glass-to-glass latency, encoder CPU under overlays, transcoding cost, uptime or auto-recovery across service restarts. OME uses a latest container tag; pinned artifacts are preferable. The bridge's session state is in memory, so restart behavior and horizontal scaling need deliberate design. The Canvas path should have frame-budget and memory profiling, especially on low-end phones. Browser-dependent camera permissions/codec support require a compatibility matrix.

Prioritized validation: automated unit tests for compositor pure functions; browser integration tests of scene changes and capture; WHIP renegotiation and reconnect tests; signature/expiry and token-reuse abuse cases; soak test at 30/60 FPS; 1/10/100 concurrent publishing sessions; CDN playback measurements; production-safe telemetry dashboards. None of these benchmark targets is claimed to have been met.
